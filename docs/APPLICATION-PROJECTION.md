# Offline selected application projection and migration rehearsal

`application.application_projection.OfflineApplicationProjection` prepares the
selected `secretary_digest_projection` class without granting it to the deployed
Engineer. The separate [commissioned gateway route](APPLICATION-COMMISSIONS.md)
and [trusted bounded scheduling loop](APPLICATION-PREPARATION.md) now prepare
generated source through actual synthetic usage journals and durable functional
health. All remain absent from default runtime assembly, the CLI, model tools
and financial RPC. Paid/live/production authorization remains false. This implements
local synthetic preparation for T22; it does not complete A42, T18 economics,
intended-host verification, immutable deployment or an owner Class C grant.

## Actual application effect

Exactly one source file, `applications/secretary_projection.py`, implements
`graph(context)`. The trusted parent obtains an actual persisted
`Secretary.digest`, verifies each report against `secretary_reports`, and exposes
only digest identity and bounded report identity, role, kind, plain summary,
evidence references and material/incident flags. Financial values, expenses,
pause/owner policy, credentials and database handles are omitted. Extraction
requires a paper portfolio and refuses a source database containing actual paid
usage receipts. After comparing immutable original records, the trusted parent
normalizes multiline report whitespace. This interface is intended exclusively
for synthetic paper fixtures; those checks do not certify arbitrary input as
synthetic or authorize production use.

The output is `{"node":"render_projection","payload":...}`. Version 1 carries
a plain title and ordered report IDs; version 2 carries a plain title and bounded
groups of report IDs under registered labels. Every supplied report must occur
exactly once, including all material and incident reports. Unknown/duplicate IDs,
missing reports, markup/control characters and extra fields fail independently.
No candidate operation can alter reports, create financial actions or authorize
deployment. An accepted result writes an actual durable synthetic application
projection into its own SQLite sidecar.

## Existing OS boundary and independent evidence

Each invocation starts the existing pinned `department_child` in a fresh
`-I -S -B` interpreter with scrubbed environment, closed descriptors and an absent
bytecode-cache prefix inside the sealed stage. Its irreversible Linux x86-64
seccomp filter is installed before candidate input parsing and compilation.
Filesystem access/mutation, sockets, process creation and parent-process access
remain denied. Existing 128 MiB, three-CPU-second and 16 KiB output limits apply;
the parent fixes a one-to-three-second deadline and 128 KiB input limit.
The generic child is called directly with the offline `render_projection`
operation. The protected financial/departmental gateway operation tuples are
unchanged.

Class-specific sealed manifests bind source path/content, output contract,
baseline source, controller/worker/sandbox/helpers, interpreter/stdlib inventory,
policy and independently selected finite corpus. Numeric-plugin manifests cannot
substitute. Private sealed `PluginStageStore` collections hold source, corpus and
HMAC-authenticated receipts; candidate code receives none of their paths, expected
outputs or keys. Controller pins must come from trusted release work; calculating
current pins in tests proves implementation behavior, not owner approval.

Validation repeats actual confined source on at most eight selected inputs and
records actual process exits and independently matched outputs. Child work is
bounded to sixty seconds; trusted hashing, validation and storage add overhead.
This demonstrates repeatability on the finite corpus only. Offline application
rendering accepts those exact pinned inputs; repeated feedback does not establish
untouched economic evidence or general determinism.

Every read and rollback-baseline effect check authenticates every durable row,
including canonical title, exact report IDs, grouped output and fixed migration
backfill. Source, receipt, class, corpus or key substitution fails. A validation
receipt alone cannot make a release a rollback baseline; the sidecar must contain
an actual authenticated application effect.

## Compatible synthetic application state

The private sidecar has only four fixed projection tables. It rejects substituted
financial databases, symlinks, hard links and scope/pin/key changes. Candidates
never receive its path, handles, SQL, migration hooks or writable mounts.
SQLite transactions and compare-and-set generation checks govern activation and
publication. No global repository migration or protected financial table changes.

The trusted parent rehearses a fixed expand/contract sequence:

1. Legacy records persist plain title and ordered `report_ids_json`.
2. Expansion adds nullable `groups_json`, authenticates existing rows and backfills
   each with the fixed `Reports` group. Legacy columns/rows remain available.
3. A validated v2 source writes both grouped output and flattened legacy IDs.
   The v1 reader consumes new records; the v2 reader supports legacy/null-group
   records. Reopening the controller verifies persisted compatibility.
4. Code rollback changes the active source pointer only. New v1 writes retain
   null groups and remain readable through the deterministic v2 fallback.
   All earlier application records, including v2 effects, remain present.
5. Destructive contraction occurs only on a newly created disposable SQLite
   backup clone. The controller fills legacy fallback groups, rebuilds the clone
   without its legacy column, retires v1 as a rollback target, reopens the clone,
   refuses legacy reading/admission and performs an actual confined v2
   render/write. The original sidecar schema, pointer and records remain intact.

A failed child or damaged active source invokes deterministic pointer recovery
without candidate/model hooks. A prior release requires verified independent
validation and actual authenticated effects. Otherwise the sidecar becomes
`MANAGE_ONLY`. A delayed failure preserves newer activation. Corrupted historical
application evidence refuses rollback rather than inventing a healthy baseline.
Protected financial reconciliation remains independent. No database snapshot is
restored during source rollback.
