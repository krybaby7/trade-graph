# Commissioned pure-feature implementation and recovery

`OfflinePluginEngineer` and `CommissionedPluginHandler` connect the existing
protected Leader/Engineer/gateway task flow to the exact sealed staging,
replay, executable bundle and functional shadow APIs. They are opt-in offline
preparation APIs, absent from runtime assembly. Default owner policy continues
to exclude `pure_feature_plugin`. The handler rejects funded providers pending
independent T18/T21 evidence and explicit owner admission. No production pointer,
financial state, deployed class permission or live permission changes here.

An independently selected `PluginCommissionPolicy` pins one capability class,
one source path, the `numeric_features/v1` interface, `stateless/v1`, exact
baseline release/source/runtime/artifact identities, protected manifest, shadow
policy and bounded local recovery count. A separate controller release hash and
private authentication key remain parent-only. A caller cannot choose a new
corpus, baseline or policy by putting those fields in model output. Computing
current fingerprints in a candidate-controlled checkout does not grant owner
authority or establish an immutable deployment image.

The active artifact baseline for this offline commission is the exact
`{"plugins/feature.py": baseline_source}` content hash. It is independently
bound to the actual sealed baseline runtime used by shadow. This artifact hash
is distinct from the baseline runtime build digest. Tests register that baseline
only in their isolated synthetic database; application defaults are unchanged.

## Durable task and cost flow

1. Persist a scoped `ChangeTask` proposal with exactly `pure_feature_plugin` and
   `plugins/feature.py`. The actual Leader worker/gateway must commission it
   under a persisted owner policy, active mandate, current baseline, monetary
   allocation, attempt bound and expiry. Synthetic fixtures explicitly install
   their synthetic class policy; production code does not install one.
2. The existing `EngineerHandler` persists the sanitized source snapshot and
   generation request, increments the shared attempt counter and dispatches
   through `ModelGateway`. The existing gateway reserves and journals each
   immutable model attempt before its provider effect. Output remains the
   bounded `EngineerPatch` grammar; no model commands, dependencies, tests,
   archives or migration hooks are accepted.
3. Before local implementation, bind the exact supplied source file map to the
   patch retained in that successful gateway invocation. Require its portfolio,
   task/root, baseline, committed reservation and retained synthetic cost
   receipts. Wrong-path and failed-validation output still retains the model
   cost. Unknown usage follows the existing gateway reconciliation path rather
   than starting local implementation.
4. Persist `engineering_attempts` before source staging or execution. The trusted
   parent stages the exact source, independently replays it, builds its exact
   executable bundle and compares it to the actual baseline in functional
   shadow. The existing confined worker executes candidate source with no file,
   network, process or credential access. Expectation values, independent case
   IDs, host/store paths, controller policy and receipt keys stay outside the
   model snapshot. Feedback contains bounded failure names and prior candidate
   source; replay/shadow reports remain in trusted storage.
5. Check the current worker lease and commission before every local effect and
   candidate publication. Persist each independently authenticated receipt as
   its stage finishes. READY/FAILED candidates and their attestations bind the
   applied Leader commission/task hash, exact baseline, generated patch,
   controller/policy, gateway invocation/reservation/cost receipts and all
   replay/build/shadow evidence. The parent authenticates the full commission
   report with its separate private key and seals it without replacing earlier
   evidence.
6. A failed replay, shadow or capability check may use the inherited bounded
   repair path. Every model repair has a fresh reservation and receipt inside
   the same root/task monetary and attempt envelope. Schema repair also uses
   the inherited one-repair limit. A crash reuses the durable model result and
   already retained local receipts, rather than issuing a new model request or
   repeating completed replay. Local recovery is capped at three independently
   selected retries per generation; receipt publication interrupted before its
   checkpoint can leave retained orphan evidence and repeat local work within
   that bound. Unknown external dispatch remains unresolved.

`verify_candidate(candidate_id)` reauthenticates the exact parent report after
restart, checks current independent pins, rechecks commission/source/cost
identity and verifies its original replay, bundle and shadow receipts. Another
key, substituted proof, altered model result or changed recorded cost cannot
transfer acceptance. The R1 activation controller refuses this separate
executable controller identity. Neither the handler nor verifier activates a
candidate.

All commission reports state `production_authorization=false`,
`live_authorization=false` and `economic_evidence=not_evaluated`. Repeated finite
replay/shadow feedback can become development data; this bounded workflow does
not make the corpus untouched, establish general determinism or prove trading
profitability. Final economic/held-out evidence must remain independently
reserved.
