# W11-B C11: The strategy lab inside the service

For the owner: The Trading desk can now write its own strategy versions, test them on stored prices and confirm them on
later days it has never seen, all inside the installed system, and it is woken with the results, so nobody has to run
practice-range commands by hand before day plans can be made. It was built and tested only with made-up prices and a
scripted desk in the cloud, so the first real results appear after the install (L3), when the desk asks its lab to
confirm the two starting strategies or new ones it writes. There is nothing new to decide: at L3 you add the word
`lab` to the Trader's list in your subscription profile (the updated checklist, step 3), and you can watch the lab's
work in HQ's activity log.

Branch: `claude/c11-strategy-lab`, head: the commit that adds this handoff's test results and pull request link (code
and tests at `5ef6c4e`). Pull request: https://github.com/krybaby7/trade-graph/pull/27 (not merged).

## What was built

- `src/trade_graph/contracts/strategy_lab.py`: `LabRequest`, the desk's request to the lab in a flat strict-provider
  shape: `register_strategy` (a `PracticeStrategy` document as JSON text), `create_study`, `tune` (coin, source,
  optional sub-window, cost profiles), `confirm`. `problem()` judges one request alone (grammar, missing or unused
  fields, window order, coin, source); `AppliedLabRequest` is what became of it when queued.
- `src/trade_graph/contracts/wakes.py`: `TraderWakeReply.lab_requests` (last field, optional, no item bound) and
  `WakeOutcome.lab_requests`; the trigger kind `lab_results` (needs a note) in `TRIGGER_KINDS`, `_TRIGGER_NEEDS` and
  `CHECK_IN_KEEPING_KINDS` (`purpose_of` gives it `event` unchanged); `WakeOutcomeRecord.lab`.
- `src/trade_graph/adapters/persistence/strategy_lab_schema.py` and `wake_schema.py`: state migration 0051 (below);
  `migrations/versions/0051_strategy_lab.py` (Alembic, after 0044); registered in `migrate.py`.
- `src/trade_graph/application/strategy_lab/queue.py`: `LabQueue`: batches (one per answer) and requests in order;
  a request refused on its own is recorded `refused` at once; `next_open`, `claim`, `put_back`, `finish` (finishes the
  batch with its last request), `unannounced`/`announce` for the wake, reads for the context.
- `src/trade_graph/application/strategy_lab/worker.py`: `StrategyLabWorker.step()` runs the oldest open request:
  register and study through the protected store; tune and confirm checked by `PracticeRangeStore.check_run`, replayed
  outside any transaction under the named profiles (all when none) and always the account's own, then every report
  and the request's end written in one transaction. A stop puts a running request back; a crash leaves it `running`
  and the next start re-runs it. Refused (a `TradeGraphError`, with the reason) or failed (unexpected, with the type).
  First step of a start: registers the two packaged examples if no strategy is registered. Records `strategy_lab`
  activities (started, each finished or interrupted request, seconds, queue counts). `account_cost_profile(execution)`.
- `src/trade_graph/application/strategy_lab/context.py`: `lab_context(...)`, the desk's `lab` key: newest results
  (each report as `summary.report_overview` and `summary.report_lines`, one per cost profile), the queue, per family
  versions/studies/runs/confirmed versions/newest studies and the walk-forward `confirmation_offer`, the instruction,
  within `LAB_CONTEXT_BYTES` (24 KiB; older results shorter, the rest counted).
- `src/trade_graph/application/strategy_lab/starting.py` and `starting/*.json`: the two examples packaged (the image
  copies only `src/trade_graph`), equal to `strategies/practice/*.v1.json` (a test checks); `pyproject.toml`
  package-data gains the glob.
- `src/trade_graph/application/strategy_lab/installation.py`: `installed_strategy_lab(runtime)`: the worker with its
  own `ReadOnlyMarketData` handle on the candle file, the paper broker's profile, activity recording; off with the
  reason if it cannot be prepared, never blocking the start.
- `src/trade_graph/application/practice_range/store.py`: `confirmation_offer(strategy_id, today=)` and
  `ConfirmationOffer` (the newest untouched days of a family, walk-forward); the rules are unchanged.
- `src/trade_graph/application/events/engine.py`: `EventEngine.lab` and `_lab_requests`: the Trader's lab requests are
  queued in the transaction that applies its answer (batch `wake:<wake_id>`), listed in the outcome; other departments'
  are refused with a note. `events/sources.py`: `TriggerSources._lab_results` wakes the desk once per finished batch
  (`lab-results:<batch id>`).
- `src/trade_graph/application/paper_service.py`: `lab_worker=`; `_run_lab` keeps one step running in its own thread
  (failures `strategy_lab:<error>`), stop/resume/shutdown like the news check.
- `src/trade_graph/application/subscription_operation.py`: builds the lab in `prepare()`, closes its handle at the end,

- `src/trade_graph/application/trader_workflow.py`: the `lab` key on wake turns and `LAB_WAKE_INSTRUCTION` (a separate
  constant); the wake report names the number of lab requests. `subscription_runtime.py`: `"lab"` in

- `src/trade_graph/kernel/authority.py`: `contracts/practice_range.py`, `application/practice_range/`,
  `contracts/strategy_lab.py`, `application/strategy_lab/` added to `PROTECTED_PATH_PREFIXES`.
- `src/trade_graph/api/hq_copy.py`: the wake log's words for `lab_results`.

## Decisions (reserved block D290–D294)

- **D290 (2026-10-20, implementation default for C11): the desk's lab requests.** The Trader's wake reply carries an
  optional `lab_requests` list with no item bound (D116; one reply is bounded by the 64 KiB model response, an
  envelope, not a count) of four kinds: `register_strategy` (the `PracticeStrategy` document as JSON text, because a
  strategy's named-key maps cannot be a strict provider schema), `create_study`, `tune`, `confirm`. The reply checks
  only the shape; `LabRequest.problem()` judges each request alone when the event engine queues the answer's requests
  in the transaction that applies the answer (one batch per wake, request ids `wake:<wake_id>:<n>`): a malformed
  strategy, a missing or unused field, windows in the wrong order are recorded `refused` with the reason at once, so
  one bad request never sinks the plans of the same answer and none is dropped. Study rules are checked when the
  request's turn comes. Only the Trader asks the lab (others are refused with a note). An answer that arrives after its
  trading day still queues its lab requests: they are research, not trading. Reason: the W11-B package, D116, D165,
  D166, D192.
- **D291 (2026-10-20, implementation default for C11): `lab_results` and migration 0051.** When every request of a
  batch has ended (done, refused or failed), a trigger source wakes the desk once (`lab-results:<batch id>`, a short
  note; the results are in `lab`); like a news alarm it keeps the desk's own check-in. State migration 0051 adds the
  kind to `wake_triggers`' CHECK list: SQLite cannot alter a CHECK, so 0051 copies the rows aside, drops and recreates
  the table with the same columns, indexes and rules, and copies every row back with its sequence; it does the same
  around it for `news_alarm_wake_routes`, whose rows name a trigger, so the foreign key holds throughout without
  switching foreign keys off inside the migration transaction. The 0035 statements stay exactly as merged (a test pins
  their hash). 0051 also adds `strategy_lab_batches` and `strategy_lab_requests` (kept, identity immutable, path
  `queued` → `running` → ended, ended final, attempts only grow, a batch finishes and is announced once). Reason: D194
  (a new kind needs a new migration), the package text.
- **D292 (2026-10-20, implementation default for C11): the worker.** One request per step in its own thread of the
  service, like the price collector (D222); it reads the candle file through its own read-only handle, never the price
  watcher's single locked connection, so a long replay cannot delay an alarm check; no trading, protection,
  reconciliation or money-limit step waits for it, and it runs under every pause (it places no order). Replays use the
  profiles named (all published ones when none is named, as the `practice-range-run` command) plus always the
  account's own (the paper broker's published profile, Kraken's starting tier by default), one data cut-off per
  request, the virtual USD10,000 and no instrument rules (as step L2). All reports of a request and its end are one
  transaction; a stop before the last replay puts the request back, a crash leaves it `running` and it is re-run
  first. `strategy_lab` activities record each start and each finished or interrupted request with the reason, the
  seconds spent and the queue counts. The `lab` key takes at most 24 KiB of the 128 KiB request (newest results in
  full, older ones without sentences, the rest counted) and offers per family the newest untouched confirmation window
  (`confirmation_offer`: from the end of the family's last tuning or confirmation window to the newest complete UTC
  day), so new collector days become new confirmation days. Reason: the package text, D116, D167.
- **D293 (2026-10-20, implementation default for C11): first start.** At the first lab step of a start, an
  installation with no registered strategy registers `slow-trend-pullback@1` and `range-reversion@1`, packaged in
  `application/strategy_lab/starting/` because the protected image copies only `src/trade_graph` (a test keeps them
  equal to `strategies/practice/*.v1.json`). It does not confirm them: confirmations are the desk's own requests (D138
  item 5: a report is evidence, not a pass mark). This replaces the missing confirmation step that step L2 found; the
  L3 checklist says what the owner sees. Reason: `planning/handoffs/L2.md` ("Finding for L3"), the package text.
- **D294 (2026-10-20, implementation default for C11): a fair test kept by protected software.** The practice range's
  contract and package (grammar, study rules, replay, report, summary, the walk-forward offer) and the lab's contract
  and package (queue, worker, context, installation, the packaged examples) are protected paths; migration 0051 is
  already under `adapters/persistence/`. The deployed Engineer cannot change how the test is kept fair. Reason: D280
  ("protected software keeps the test fair"), AGENTS.md.
