# W10-B C8: Money checks and the scorecard stay fast

For the owner: The safety check that runs every few seconds (your daily loss limit and the caps per coin), HQ's
"today's loss" and the scorecard used to read every price ever recorded, so they would have slowed down week by week
during the scored test; now they read only the newest price of each coin you hold (and the scorecard only the prices
of a coin while it is held), and on four made-up weeks of prices they give exactly the same answers, the money check
in about 0.01 seconds instead of about 12 and the scorecard in under a second instead of about 5. Nothing is missing
for this part; one small check inside the scorecard still looks over all the period's prices, which costs about a
third of a second and could be removed later with an extra database index. You need to do nothing: the change is
part of the normal install (step L3), with no new database step.

Branch: `claude/c8-fast-money-checks`, head: the commit that adds this handoff (code at `c059b55`). Pull request:
see the pull request opened from this branch into `claude/day-trader-engine-20261012` (not merged).

## What was built

- `src/trade_graph/application/ledger.py`:
  - `Ledger.newest_mark(portfolio_id, asset, at)` and `NEWEST_MARK_SQL`: the mark the books use for one coin
    (`... WHERE portfolio_id=? AND asset=? AND observed_at<=? ORDER BY observed_at DESC, rowid ASC LIMIT 1`), one
    row through `valuation_marks_newest` (migration 0044).
  - `_marks(portfolio_id, at, books)` now returns only the newest mark of each coin the books hold (it used to
    return every mark of the portfolio up to `at`, with no asset filter and no limit, which `kernel/books.py`
    `_latest_mark` then searched for each lot). The kernel is unchanged and picks the same mark.
  - `_newest_rates(at, currencies, target, inverse=)` and `NEWEST_RATE_SQL`: for each currency a valuation may
    convert, the one rate `kernel.books._convert` would pick (newest reference date known then, newest retrieval,
    last recorded of exact ties); nothing is read when no conversion is needed. Used by `equity`, `native_equity`,
    `fx_rate`, `reporting_value` and `native_value`. `_rates` (every rate up to a time) is unchanged and still used
    by `performance` (flows are valued at their own times) and by the forward producer's per-fill EUR values.
  - `performance` reads the end marks and rates once instead of twice.
- `src/trade_graph/application/money_limits.py` (protected path): `_marks_fresh` reads the ledger's
  `newest_mark` (it broke ties with `rowid DESC`; it reads only the time, so no result changes).
- `src/trade_graph/application/execution.py`: `_native_mark` (a coin's value in the per-coin cap of
  `authorize`) reads the ledger's `newest_mark` (it broke ties with `rowid DESC`; see D271).
- `src/trade_graph/application/scorecard.py` (protected path): `_curve` reads each coin's prices only while it is
  held (`_held` works out the windows from the books at the start and the period's postings, exactly as the curve
  applies them), the newest price when a posting makes a coin held, and every coin's newest price at the end. The
  check that refuses a price in another currency is unchanged. `compute_scorecard`'s signature and document are
  unchanged.
- Tests (new): `tests/integration/test_mark_reads.py` (rows read stay the same after ten times the history; every
  mark read seeks one coin through the index (EXPLAIN QUERY PLAN); the scorecard reads a coin's prices only while
  held; ties between marks of one moment are broken as the ledger does), `tests/property/test_mark_read_properties.py`
  (Hypothesis: the reads as they were at `f6abbd8` are kept in the test as the reference, and the new reads give

## Decisions (reserved block D269–D273)

- **D269 (2026-10-18, implementation default for C8): a valuation reads only the newest mark of each coin held.**
  `Ledger.equity`, `native_equity` and `performance` read one mark per coin the books hold at the moment
  (`Ledger.newest_mark`, `LIMIT 1` through `valuation_marks_newest`), not every mark of the portfolio. The kernel
  (`kernel/books.py`) is unchanged and chooses the same mark it chose from the whole list, so every value is the
  same. Callers that gain: the paper service's money-limit step on every tick, HQ's today's loss, the per-order
  checks in `Execution.authorize`, the Trader workflow's and the Secretary's equity, and the forward producer. On a
  database without the index (the forward producer's in-memory copy of retained records) each coin is one scan of
  that small copy. Reason: the night report's "Left for later" and the C8 package; AGENTS.md (no change to money
  arithmetic).
- **D270 (2026-10-18, implementation default for C8): a valuation reads only the newest rate of each pair it may
  need.** For every currency a valuation may convert (cash, prices, costs, flows), the ledger reads the one rate
  `_convert` would have chosen from every rate (newest of `max(observed_at, valid_as_of)`, then newest
  `retrieved_at`, and of exact ties the last recorded), and for exposure checks the opposite pair too; a USD
  account valued in USD reads no rate at all. `_rates` (every rate up to a time) stays for `performance`, whose
  deposits and withdrawals are valued at their own times, and for the forward producer's per-fill values. No index
  was added for `fx_rates`: the paper feed records one reference rate an hour (about 24 rows a day, 673 in four
  weeks), so the per-pair read stays small; it returns one row to Python instead of all of them. Reason: the C8
  package ("do the same for `_rates` if it reads every FX rate").
- **D271 (2026-10-18, implementation default for C8): one rule for "the newest mark".** A coin's mark at a moment
  is the newest observed at or before it, and of marks stamped with the very same time the first recorded (lowest
  `rowid`): what the ledger always chose (its unordered read returned ties in `rowid` order and `max` kept the
  first) and what the scorecard documented (D200). `Ledger.newest_mark` holds it, and the money-limit step's
  freshness check (`money_limits.py`) and a coin's value in the per-coin cap (`Execution._native_mark`) now read it
  instead of their own `rowid DESC` queries. For `money_limits.py` nothing changes (it reads only the time). For
  `_native_mark` it changes which of two marks with the exact same timestamp values a coin in the per-coin cap, so
  the cap and the account's value in the same check use the same price (before, the cap used the last recorded and
  the equity the first). Timestamps carry microseconds and each mark takes its own, so this needs two marks of one
  coin in the same microsecond (a frozen test clock). Reason: the C8 package ("align it with the ledger").
- **D272 (2026-10-18, implementation default for C8): the scorecard reads the prices its curve needs.** The equity
  curve has a point after every posting and at every new price of a coin held (D200), so it now reads each coin's
  prices from the posting that makes it held to the posting that empties it (or the end of the period), the newest
  price when it becomes held, and each coin's newest price at the start and the end. The points, the worst
  drawdown, the marks left for the end valuation and the whole document (`scorecard_sha256` included) are the same
  as when every price of every coin held in the period was read (property test against the old `_curve`). Not done:
  (1) the check that refuses a price recorded in another currency still asks the database about every price of
  those coins in the period; it returns nothing but is about 0.34 of the 0.76 seconds at four weeks; making it
  bounded needs a second index on the largest table (written on every price), not worth it for a read HQ makes at
  most once a minute; (2) HQ's cache is not made incremental: the scorecard is a protected scoring definition and
  carrying state between refreshes risks drifting from a fresh computation. A coin held the whole period still has
  every price read, because each is a point. Reason: the C8 package ("read only what it needs, or update HQ's cache
  incrementally") and D204.
- **D273 (2026-10-18, implementation default for C8): no migration, and reads are measured by counts.** Every new
  read is served by migration 0044's `valuation_marks_newest`; the reserved state migration 0048 is unused. Tests
  assert on statements run, rows returned per table and SQLite virtual-machine steps (`ReadMeter`), never on
  seconds, so they do not depend on machine load; seconds are reported only as information. Reason: the C8 package
  and waves 8 and 9's experience with speed-dependent tests.
